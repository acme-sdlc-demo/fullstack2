# Area analysis: frontend

## What it does
Per the code graph, the area named `frontend` (distinct from the sibling areas `frontend/routes`, `frontend/components`, `frontend/client` and `frontend/hooks`, which are analysed separately) contains exactly one file at this commit: `frontend/openapi-ts.config.ts`, 21 lines [cite: frontend/openapi-ts.config.ts]. Its job is not application logic but build-time configuration: it tells the `@hey-api/openapi-ts` generator how to turn the backend's OpenAPI schema into the TypeScript API client the rest of the frontend calls. Concretely it is a `defineConfig` call that sets `input: "./openapi.json"` and `output: "./src/client"` and configures three plugins — `@hey-api/client-axios` with `throwOnError: true`, `@hey-api/typescript` with `case: "preserve"`, and `@hey-api/sdk` with `strategy: "byTags"`, `methods: "static"`, `containerName: "{{name}}Service"` and a `methodName` that strips the OpenAPI tag prefix off each operation ID [cite: frontend/openapi-ts.config.ts:3-20]. Per the team, this Project is an unmodified pilot of the generic FastAPI full-stack template (Users/Items, no real data, no live deployment) [cite: source:transcript-run-1416470e@r1#T3], and the frontend client this file configures is confirmed by the same conversation as fully generated, never hand-edited: "The frontend client in frontend/src/client is generated from the backend OpenAPI schema, so it is not edited by hand" [cite: source:transcript-run-1416470e@r1#T1].

## Main flows
1. **Manual/CI client regeneration.** A developer or CI runs `bash ./scripts/generate-client.sh` [cite: frontend/README.md:48-51, scripts/generate-client.sh:1]. The script `cd backend` and runs `FASTAPI_ENV=development uv run python -c "import app.main; import json; print(json.dumps(app.main.app.openapi()))"`, capturing the live FastAPI app's OpenAPI document as JSON into `../openapi.json` [cite: scripts/generate-client.sh:6-7]. It `mv`s that file to `frontend/openapi.json` [cite: scripts/generate-client.sh:9], then runs `bun run --filter frontend generate-client`, which runs `openapi-ts` inside `frontend/` [cite: scripts/generate-client.sh:10, frontend/package.json:11]. The CLI reads this area's `openapi-ts.config.ts`, loads `./openapi.json` as `input`, and writes the generated files into `./src/client` as `output` using the three configured plugins [cite: frontend/openapi-ts.config.ts:4-20]. It ends by writing every file under `frontend/src/client/**.gen.ts` (service classes, types, Axios client runtime, e.g. `frontend/src/client/sdk.gen.ts:1`) and then runs `bun run lint` to reformat/fix the output [cite: scripts/generate-client.sh:11].
2. **Pre-commit auto-regeneration on backend or config change.** A commit that touches `backend/app/*.py`, `backend/pyproject.toml`, `uv.lock` or this file itself [cite: .pre-commit-config.yaml:67] triggers the same `generate-client.sh` entry (flow 1) as the `generate-frontend-sdk` pre-commit hook [cite: .pre-commit-config.yaml:62-66], so a backend schema change or an edit to this config is expected to regenerate `frontend/src/client` as part of the same commit rather than drift from it.
3. **CI Playwright job depends on this step succeeding before any test runs.** `.github/workflows/playwright.yml` runs `uv sync` in `backend`, `bun ci` in `frontend`, then `bash scripts/generate-client.sh`, then `docker compose build` and `docker compose run --rm playwright bunx playwright test ...` [cite: .github/workflows/playwright.yml:72-78]. If this config's `input`/`output` paths or plugin options are wrong, generation fails or produces a client whose shapes don't match what `frontend/src/components`, `frontend/src/routes` and `frontend/src/hooks` expect, and the whole job fails before Docker is even built — a generation error, not a test failure. Reads: the backend's running OpenAPI schema (via `app.main.app.openapi()` [cite: scripts/generate-client.sh:7]); writes: `frontend/src/client/**.gen.ts`.
4. **Manual developer flow without the script.** `frontend/README.md:56-66` documents downloading the OpenAPI JSON from a running backend (`http://localhost:8000/api/v1/openapi.json`) to `frontend/openapi.json` by hand, then running `bun run generate-client` directly — the same `openapi-ts` CLI reading this same config [cite: frontend/README.md:60-65, frontend/package.json:11].

## Where it's fragile
- **The code graph could not index this file for symbols** — it was "read for imports only" because no tsconfig/source-set in the frontend build includes it [facts above; cite: frontend/openapi-ts.config.ts]. That means `bun run build` (the gate's frontend build step, `tsc -p tsconfig.build.json && vite build` [cite: frontend/package.json:8]) never type-checks this file; a typo in a plugin option would only surface when `openapi-ts` itself runs, i.e. during `generate-client.sh`, not during the normal lint/build gate. Before changing this file, actually run `bash scripts/generate-client.sh` (needs an importable/runnable backend) and diff the resulting `frontend/src/client/**` rather than trusting `bun run build` alone.
- **It is the area's one hotspot by the graph's own count (score 21, 1 commit × 21 lines)** [facts above], which at this file's size just reflects that the whole file changed once; there is no history yet showing which lines are edited most often. Treat the whole file as equally sensitive until more commits accumulate.
- **No test anywhere exercises this config directly.** No `*.test.ts`/`*.spec.ts` targets `openapi-ts.config.ts`, and it is excluded from the TypeScript build the graph indexed, so a bad edit is only caught by (a) `generate-client.sh` failing outright, (b) the generated `frontend/src/client` no longer matching its callers, which `bun run build` would catch once that mismatch exists as a type error, or (c) the gate's Playwright e2e suite failing against a client that silently produced wrong request shapes. After any change here, regenerate, then run `bun run build` and the Playwright suite rather than relying on lint/ruff/mypy-equivalent checks to catch anything in this file.
- **The `methodName` regex `name.replace(/^[^-]*-/, "")`** [cite: frontend/openapi-ts.config.ts:17] strips everything up to and including the first `-` in each generated operation ID to produce the method name on each `*Service` class (e.g. the generated `UsersService.readUserMe`). This assumes every backend route's OpenAPI `operation_id` follows a `tag-methodName` shape, which matches FastAPI's default `operation_id` (`{function_name}` prefixed by the router's tag) for the routes read here, e.g. `@router.get("/me", ...)` in `backend/app/api/routes/users.py:124` and `@router.post("/", ...)` in `backend/app/api/routes/items.py:61`. A route added without that convention (a custom `operation_id`, or a tag containing no `-`-separator boundary FastAPI expects) would get an unexpected generated method name with nothing in this file or the build gate checking that; after any backend route change, regenerate and read the resulting `frontend/src/client/sdk.gen.ts` method names before trusting them.
