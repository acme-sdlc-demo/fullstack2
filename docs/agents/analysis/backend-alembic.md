# backend/alembic

## What it does
This area is the backend's schema-migration machinery: it turns the SQLModel table definitions in `app/models.py` into versioned, ordered SQL steps that bring a Postgres database from empty to the shape the app code expects, and back. `env.py` wires Alembic's `context` to the app's `SQLModel.metadata` and to `settings.DATABASE_URL` [cite: backend/app/alembic/env.py:22,25,34], and the five scripts under `app/alembic/versions/` are the ordered steps themselves, chained by each one's `revision`/`down_revision` pair (e.g. `e2412789c190` → `9c0a54914c78` → `d98dd8ec85a3` → `1a31ce608336` → `fe56fa70289e`) [cite: backend/app/alembic/versions/e2412789c190_initialize_models.py:13-14, backend/app/alembic/versions/9c0a54914c78_add_max_length_for_string_varchar_.py:14-15, backend/app/alembic/versions/d98dd8ec85a3_edit_replace_id_integers_in_all_models_.py:15-16, backend/app/alembic/versions/1a31ce608336_add_cascade_delete_relationships.py:14-15, backend/app/alembic/versions/fe56fa70289e_add_created_at_to_user_and_item.py:14-15]. There are no classes/functions here that other areas import; its only "API" is the `alembic` CLI reading `backend/alembic.ini`, which points `script_location` at `app/alembic` [cite: backend/alembic.ini:5].

## Main flows
**1. Applying migrations to a fresh or existing database (`alembic upgrade head`)**
1. The CLI reads `backend/alembic.ini`'s `script_location` and loads `app/alembic/env.py` [cite: backend/alembic.ini:5].
2. `env.py` builds `config` from `context.config`, sets up logging from the ini file, and imports `app.models.SQLModel` and `app.core.config.settings` so the migration run knows both the target schema and the real database URL [cite: backend/app/alembic/env.py:9,13-14,22-23,25].
3. `get_url()` returns `str(settings.DATABASE_URL)` [cite: backend/app/alembic/env.py:33-34], which is read from the Project's environment/`.env` by `Settings` [cite: backend/app/core/config.py:31].
4. Because `context.is_offline_mode()` is false in normal use, `run_migrations_online()` creates an `engine_from_config` with `poolclass=pool.NullPool`, opens one connection, and calls `context.configure(..., compare_type=True)` then `context.run_migrations()` inside a transaction [cite: backend/app/alembic/env.py:58,65-80].
5. Alembic walks the revision chain from the database's current `alembic_version` up to `head`, running each version file's `upgrade()` in order — e.g. `e2412789c190` creates `user` and `item` tables [cite: backend/app/alembic/versions/e2412789c190_initialize_models.py:21-45], then `9c0a54914c78` bounds the string columns to 255 chars [cite: backend/app/alembic/versions/9c0a54914c78_add_max_length_for_string_varchar_.py:20-43], then `d98dd8ec85a3` swaps integer PKs for `uuid-ossp`-generated UUIDs [cite: backend/app/alembic/versions/d98dd8ec85a3_edit_replace_id_integers_in_all_models_.py:21-55], then `1a31ce608336` makes `item.owner_id` non-nullable and `ON DELETE CASCADE` [cite: backend/app/alembic/versions/1a31ce608336_add_cascade_delete_relationships.py:20-27], then `fe56fa70289e` adds nullable `created_at` columns [cite: backend/app/alembic/versions/fe56fa70289e_add_created_at_to_user_and_item.py:20-24]. End result: a Postgres schema matching `app/models.py`'s `User` and `Item` tables.

**2. Container startup (`prestart.sh`)**
1. `prestart.sh` runs `alembic upgrade head` first [cite: backend/scripts/prestart.sh:7], triggering flow 1 end to end.
2. It then runs `python app/initial_data.py` [cite: backend/scripts/prestart.sh:10], which depends on the schema flow 1 just applied — writes: whatever seed rows `initial_data.py` inserts into the now-current tables.

**3. Authoring a new migration (developer/agent flow, not exercised by tests)**
1. A schema change is made in `app/models.py` (outside this area).
2. `alembic revision --autogenerate` loads `env.py`, which diffs the live DB against `SQLModel.metadata` (`target_metadata`) using `compare_type=True` [cite: backend/app/alembic/env.py:25,51,76].
3. Alembic writes a new file under `app/alembic/versions/` using the project's template, `script.py.mako` [cite: backend/alembic.ini:5] (template file itself not read in this pass), with a fresh `revision` and `down_revision` set to the current head — the pattern every existing version file follows [cite: backend/app/alembic/versions/fe56fa70289e_add_created_at_to_user_and_item.py:14-15].
4. The new file must be reviewed/adjusted by hand, since Alembic's autogenerate comment says so verbatim in every version file here ("commands auto generated by Alembic - please adjust!") [cite: backend/app/alembic/versions/e2412789c190_initialize_models.py:20, backend/app/alembic/versions/fe56fa70289e_add_created_at_to_user_and_item.py:21].

## Where it's fragile
- `env.py` is the area's one hotspot (score 86, 86 lines in its one commit) [cite: backend/app/alembic/env.py:1-86] — it is the only place that resolves the real `DATABASE_URL` and metadata for every migration run; a mistake here (e.g. changing `compare_type`, the `NullPool`, or the `get_url()` lookup) breaks every `alembic upgrade`/`revision` call rather than one migration. Check it by running the gate's own build step, `FASTAPI_ENV=development $python -m alembic upgrade head`, against a disposable database [cite: CLAUDE.md:45].
- The `d98dd8ec85a3` migration (integer → UUID primary keys) runs raw SQL (`op.execute`) to populate and rename columns and depends on `uuid-ossp` being installable and on the exact column rename order; it has no automated test here, and getting the order wrong (e.g. dropping `item.owner_id` before `item.new_owner_id` is populated) would corrupt the `item`→`user` relationship [cite: backend/app/alembic/versions/d98dd8ec85a3_edit_replace_id_integers_in_all_models_.py:26-55]. There is no test file for this area (0 test files in the code graph's summary for `backend/app/alembic`), so the only check is actually running `alembic upgrade head`/`downgrade` end to end, which the gate's build step does once per run [cite: CLAUDE.md:45,48].
- Migration scripts are generated, point-in-time SQL; they must never be edited after being applied anywhere, only appended to via a new revision — this is implicit in the `down_revision` chain (editing an old file breaks `alembic downgrade`/`upgrade` for anyone who already ran it) [cite: backend/app/alembic/versions/e2412789c190_initialize_models.py:13-14] [general knowledge].
- `fe56fa70289e` adds `created_at` as `nullable=True` at the DB level [cite: backend/app/alembic/versions/fe56fa70289e_add_created_at_to_user_and_item.py:22-23], while `app/models.py`'s `User.created_at`/`Item.created_at` have a non-null `default_factory` [cite: backend/app/models.py:83,132]: existing rows created before this migration can have `NULL` `created_at`, so code reading that column must tolerate `None` even though new rows won't have it — a mismatch between the migration's nullability and the model's apparent intent that is easy to miss when changing either side.

- Uses `backend/core`: `env.py` imports `app.core.config.settings` to get `DATABASE_URL` [cite: backend/app/alembic/env.py:23,34], and `backend` more broadly via `app.models.SQLModel` as the autogenerate target [cite: backend/app/alembic/env.py:22,25].
- Used by areas: none found in the code graph — no other backend or frontend code imports from `app/alembic`; it is only driven by the `alembic` CLI via `backend/alembic.ini:5` and `backend/scripts/prestart.sh:7`.
- Libraries: SQLAlchemy 2.1.6 (`engine_from_config`, `pool`, `sa.Column` etc.) [cite: backend/app/alembic/env.py:5], alembic 1.20.1 (`context`, `op`) [cite: backend/app/alembic/env.py:13, backend/app/alembic/versions/e2412789c190_initialize_models.py:10], sqlmodel 0.0.48 (`SQLModel`, `sqlmodel.sql.sqltypes.AutoString`) [cite: backend/app/alembic/env.py:22, backend/app/alembic/versions/e2412789c190_initialize_models.py:9], python-stdlib 3.11 (`os`, `logging.config.fileConfig`) [cite: backend/app/alembic/env.py:1-2].
- Outside the repository: a real Postgres database, reached via `settings.DATABASE_URL` [cite: backend/app/alembic/env.py:34, backend/app/core/config.py:31], including the Postgres-only `uuid-ossp` extension that `d98dd8ec85a3` creates [cite: backend/app/alembic/versions/d98dd8ec85a3_edit_replace_id_integers_in_all_models_.py:23].
