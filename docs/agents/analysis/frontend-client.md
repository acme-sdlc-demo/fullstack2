# Area analysis: frontend/client

## What it does
This area is the typed bridge between the React frontend and the FastAPI backend: every HTTP call the UI makes (login, users, items, utils, and a test-only private endpoint) goes through it instead of a hand-written `fetch`/`axios` call. It is entirely generated code — every file in it starts "This file is auto-generated by @hey-api/openapi-ts" [cite: frontend/src/client/sdk.gen.ts:1], produced by the `@hey-api/openapi-ts` generator configured in `frontend/openapi-ts.config.ts:3-21`, which reads `./openapi.json` and writes into `./src/client` using the `@hey-api/client-axios`, `@hey-api/typescript` and `@hey-api/sdk` plugins [cite: frontend/openapi-ts.config.ts:7-19]. The main types that do the work are the five service classes in `sdk.gen.ts`: `LoginService` [cite: frontend/src/client/sdk.gen.ts:21], `UsersService` [cite: frontend/src/client/sdk.gen.ts:99], `UtilsService` [cite: frontend/src/client/sdk.gen.ts:260], `ItemsService` [cite: frontend/src/client/sdk.gen.ts:287] and `PrivateService` [cite: frontend/src/client/sdk.gen.ts:367] — plus the one shared `client` instance built by `createClient`/`createConfig` [cite: frontend/src/client/client.gen.ts:16] and the request/response shapes in `types.gen.ts`, e.g. `ItemPublic` [cite: frontend/src/client/types.gen.ts:64] and `UserPublic` [cite: frontend/src/client/types.gen.ts:218]. The `client/` subfolder (`client.gen.ts`, `types.gen.ts`, `utils.gen.ts` under `client/client/`) and the `core/` subfolder are the generator's generic Axios-client runtime, not specific to this backend's shapes [cite: frontend/src/client/client/client.gen.ts:1-10].

## Entry points
Nothing in this area is a route or a `main`; it is a library other areas call into. The graph's "what other areas use of it" and a grep of `frontend/src` agree:
- The barrel re-exports `ItemsService`, `LoginService`, `Options`, `PrivateService`, `UsersService`, `UtilsService` from `sdk.gen.ts` and every type from `types.gen.ts` [cite: frontend/src/client/index.ts:3-4]; 20 files under `frontend/components`, `frontend/hooks`, `frontend/routes` and `frontend/tests` import from it, per the graph's entry for `index.ts` as a namespace used in those areas.
- `frontend/src/hooks/useAuth.ts:4-10` imports `Body_login_login_access_token`, `LoginService`, `UserPublic`, `UserRegister` and `UsersService`, then calls `UsersService.readUserMe()` [cite: frontend/src/hooks/useAuth.ts:25], `UsersService.registerUser()` [cite: frontend/src/hooks/useAuth.ts:31] and `LoginService.loginAccessToken()` [cite: frontend/src/hooks/useAuth.ts:42].
- `frontend/src/main.tsx:11` imports the shared `client` from `client.gen.ts` and calls `client.setConfig({...})` once at startup [cite: frontend/src/main.tsx:17-20].
- Components under `frontend/src/components/Admin`, `frontend/src/components/Items` and `frontend/src/components/UserSettings` (14 files per the graph's "Used by areas") call `UsersService`/`ItemsService` methods directly for create/update/delete forms, e.g. `UsersService.createUser()` [cite: frontend/src/client/sdk.gen.ts:119] and `ItemsService.updateItem()` [cite: frontend/src/client/sdk.gen.ts:353].
- Routes under `frontend/src/routes` (7 files per the graph) call, among others, `UsersService.readUsers()` [cite: frontend/src/client/sdk.gen.ts:105], `ItemsService.readItems()` [cite: frontend/src/client/sdk.gen.ts:293] and `LoginService.recoverPassword()`/`resetPassword()` [cite: frontend/src/client/sdk.gen.ts:59] [cite: frontend/src/client/sdk.gen.ts:72].
- `PrivateService.createUser()` [cite: frontend/src/client/sdk.gen.ts:373] is used only by `frontend/tests` (2 files per the graph), to seed a user through the test-only `/api/v1/private/users/` route.

## Main flows
1. **App start-up configures the one shared client.** `main.tsx` imports `client` from `client.gen.ts` [cite: frontend/src/main.tsx:11] and calls `client.setConfig({ baseURL: import.meta.env.VITE_API_URL ?? "", auth: () => localStorage.getItem("access_token") || "" })` [cite: frontend/src/main.tsx:17-20]. `setConfig` [cite: frontend/src/client/client/client.gen.ts:27] merges this into the module-level `_config` and the underlying Axios `instance.defaults` [cite: frontend/src/client/client/client.gen.ts:28-34], so every later call made through `client` — there is one shared instance, not one per call [cite: frontend/src/client/client.gen.ts:16] — carries this `baseURL` and `auth` callback. This writes an in-memory config object and the Axios instance's defaults; it makes no network call.
2. **Login sets the token every later authenticated call reads.** `useAuth`'s `login` function calls `LoginService.loginAccessToken({ body: data })` [cite: frontend/src/hooks/useAuth.ts:42-44], which calls `(options.client ?? client).post(...)` against `/api/v1/login/access-token` with a form-encoded body [cite: frontend/src/client/sdk.gen.ts:27-38]. On success, `useAuth` writes the returned `access_token` into `localStorage` [cite: frontend/src/hooks/useAuth.ts:45]. Any later call whose generated method sets `security: [{ scheme: 'bearer', type: 'http' }]` — e.g. `UsersService.readUserMe` [cite: frontend/src/client/sdk.gen.ts:152] or `ItemsService.readItems` [cite: frontend/src/client/sdk.gen.ts:296] — has `beforeRequest` run `setAuthParams(opts)` [cite: frontend/src/client/client/client.gen.ts:52-53], which uses `getAuthToken` to turn the callback's return value into an `Authorization: Bearer <token>` header [cite: frontend/src/client/core/auth.gen.ts:22-33]. This reads `localStorage["access_token"]` and writes the `Authorization` header of the outgoing request.
3. **A CRUD form submits and the list it populates is kept in sync.** A component such as one under `frontend/src/components/Items` calls `ItemsService.createItem({ body })` [cite: frontend/src/client/sdk.gen.ts:307-318], which posts to `/api/v1/items/` carrying the bearer header from step 2 and a JSON `Content-Type` [cite: frontend/src/client/sdk.gen.ts:308-316]; the live backend route handling that path is `read_items`/`create_item` in `items.py` [cite: backend/app/api/routes/items.py:13] [cite: backend/app/api/routes/items.py:61]. The response is typed as `itemsCreateItemResponses` built on `ItemPublic` [cite: frontend/src/client/types.gen.ts:825] [cite: frontend/src/client/types.gen.ts:64]. A route such as one under `frontend/src/routes/_layout` separately calls `ItemsService.readItems()` [cite: frontend/src/client/sdk.gen.ts:293-299], typed as `ItemsPublic` whose `data` field is `Array<ItemPublic>` [cite: frontend/src/client/types.gen.ts:104] [cite: frontend/src/client/types.gen.ts:108]. This reads/writes the backend's `items` table through those routes.
4. **A 401/403 from any call forces a logout, regardless of which service made the call.** Every generated service method funnels through the one `client` instance created with `throwOnError: true` [cite: frontend/src/client/client.gen.ts:16], so a failed request throws an `AxiosError`. `main.tsx` builds its `QueryClient` with `queryCache`/`mutationCache` set to `onError: handleApiError` [cite: frontend/src/main.tsx:31-38], and `handleApiError` checks `error instanceof AxiosError && [401, 403].includes(error.response?.status ?? 0)`, then removes `access_token` from `localStorage` and redirects to `/login` [cite: frontend/src/main.tsx:22-29]. This reads the Axios error's `response.status` and writes `localStorage` and `window.location.href`.

## Where it's fragile
- **Every file here is generated, so a hand-edit is lost on the next regeneration, and there is no test file inside this area itself.** A grep for `*client*.test.*`/`*client*.spec.*` under `frontend` found none; correctness is checked only indirectly, by the callers' own tests and by the Playwright suite the gate runs against the live backend. Before changing anything under `frontend/src/client`, check whether the real fix belongs in `frontend/openapi-ts.config.ts:3-21` (generator config) or in the backend's OpenAPI schema (a route or Pydantic model), then regenerate with the `generate-client` script [cite: frontend/package.json:11] [cite: scripts/generate-client.sh:1-11] rather than hand-editing a `*.gen.ts` file.
- **`types.gen.ts` is the hotspot of the area (947 lines, 2 commits) and nearly every other caller depends on it.** The graph's "what other areas use of it" list shows dozens of entries pointing into this one file, e.g. `UserPublic` used in 5 files [cite: frontend/src/client/types.gen.ts:218] and `ItemPublic` used in 3 files [cite: frontend/src/client/types.gen.ts:64]. A field added, renamed or re-typed on a backend model ripples silently into every component that destructures it; after regenerating, run the frontend build (the gate's `bun run build` step) to catch breakage at compile time.
- **The shared `client` singleton carries mutable, process-wide config (`baseURL`, `auth`) set once at startup.** `client.gen.ts` creates it with only `throwOnError: true` [cite: frontend/src/client/client.gen.ts:16]; `baseURL` and `auth` are only added later by `main.tsx`'s `setConfig` call [cite: frontend/src/main.tsx:17-20]. Any code path that calls a service method before that `setConfig` runs gets a request with no `baseURL`/`auth`; `frontend/tests` imports the same generated services through `PrivateService.createUser()` [cite: frontend/src/client/sdk.gen.ts:373] for Playwright setup, so a change to startup configuration should be checked against that test path too.
- **Error typing is coarse for endpoints with no declared error schema.** `UsersService.readUserMe` and `deleteUserMe` type their error channel as `unknown` [cite: frontend/src/client/sdk.gen.ts:152] [cite: frontend/src/client/sdk.gen.ts:138], while most other methods use a generated `*Errors` union built on `HTTPValidationError` [cite: frontend/src/client/types.gen.ts:40]. This follows the backend's declared OpenAPI responses, so if a caller needs a typed error here, the fix belongs in the backend route's response model, not in this generated file.

Session state lives in the browser's `localStorage` under the key `access_token` [cite: frontend/src/hooks/useAuth.ts:45] [cite: frontend/src/main.tsx:19].

## What we don't know
- `frontend/openapi-ts.config.ts` was read by the graph's indexer for imports only, not for symbols, because no build (source set, tsconfig or project) names it [per the graph's "Not indexed" list]; what this analysis says about it comes from reading the file directly [cite: frontend/openapi-ts.config.ts:1-21], not from the graph's symbol facts.
- The generator's input, `openapi.json`, is produced at generation time by running the backend app and dumping its OpenAPI schema [cite: scripts/generate-client.sh:7], then moved into `frontend/` and consumed by `generate-client` [cite: scripts/generate-client.sh:9-10]; this file is not committed under `frontend/src/client` and this analysis does not cover it, so how current the generated client is relative to the backend's actual routes at any given moment cannot be checked from this area alone.
- Which value `import.meta.env.VITE_API_URL` takes in dev, CI and (per the team) an environment that does not exist, since this Project is not deployed anywhere [cite: source:transcript-run-1416470e@r1#T3], is set outside the repository and was not inspected here; the real `baseURL` used by `client` [cite: frontend/src/main.tsx:18] in any given run is unconfirmed from code alone.
- No test file dedicated to this area was found. Whether the team considers the Playwright suite under `frontend/tests` sufficient coverage for a change made only inside `frontend/src/client`, or expects a unit-test boundary here too, is a question for the team, not answerable from the code alone.
