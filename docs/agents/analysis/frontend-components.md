# Area analysis: frontend/components

## What it does
This area is the frontend's component library: the forms, tables, dialogs and chrome (sidebar, settings, auth shell) that the route pages compose, plus a shadcn/Radix-based UI kit the rest of the app builds on. It covers three kinds of work: admin user management (create/edit/delete users, list them in a table), item management (same CRUD shape for the template's generic "items"), and the signed-in user's own account (profile, password, delete account) and app chrome (sidebar navigation, theme). Main types: `AddUser`/`EditUser`/`DeleteUser`/`UserActionsMenu` [cite: frontend/src/components/Admin/AddUser.tsx:55, frontend/src/components/Admin/EditUser.tsx:59, frontend/src/components/Admin/DeleteUser.tsx:27, frontend/src/components/Admin/UserActionsMenu.tsx:19], `AddItem`/`EditItem`/`DeleteItem`/`ItemActionsMenu` [cite: frontend/src/components/Items/AddItem.tsx:40, frontend/src/components/Items/EditItem.tsx:45, frontend/src/components/Items/DeleteItem.tsx:27, frontend/src/components/Items/ItemActionsMenu.tsx:18], `DataTable` [cite: frontend/src/components/Common/DataTable.tsx:46], `AppSidebar`/`Main`/`User` [cite: frontend/src/components/Sidebar/AppSidebar.tsx:20, frontend/src/components/Sidebar/Main.tsx:23, frontend/src/components/Sidebar/User.tsx:43], and `ThemeProvider` [cite: frontend/src/components/theme-provider.tsx:31]. Per the team, this is a generic items-and-users template app with no live deployment and no real data; the profile's "veterinary clinic" line does not apply here [cite: source:transcript-run-1416470e@r1#T3].

## Main flows

**Admin manages a user**
1. A route renders `AppSidebar()`, which only shows the "Admin" nav item to a superuser, read from `useAuth` [cite: frontend/src/components/Sidebar/AppSidebar.tsx:20-25].
2. The admin route renders `DataTable()` with `Admin/columns.tsx`'s `columns`, built on `UserPublic & { isCurrentUser }` [cite: frontend/src/components/Common/DataTable.tsx:46, frontend/src/components/Admin/columns.tsx:9-13].
3. `AddUser` opens a `Dialog`, validates email/password/confirm_password with a zod schema (password required, must match) [cite: frontend/src/components/Admin/AddUser.tsx:34-51], and on submit calls `UsersService.createUser` through a `useMutation`, invalidating the `["users"]` query on success [cite: frontend/src/components/Admin/AddUser.tsx:74-85].
4. Each row's `UserActionsMenu` hides itself for the signed-in user [cite: frontend/src/components/Admin/UserActionsMenu.tsx:23-25] and otherwise renders `EditUser`/`DeleteUser`, which call `UsersService.updateUser` / `UsersService.deleteUser` and invalidate `["users"]` / all queries [cite: frontend/src/components/Admin/EditUser.tsx:76-88, frontend/src/components/Admin/DeleteUser.tsx:33-47].
Ends by writing to the backend's Users API; the table re-reads via React Query invalidation, never a direct re-fetch call in this area.

**Admin/owner manages an item** (same shape as users)
1. `DataTable()` renders `Items/columns.tsx`'s `columns`, including a `CopyId` cell using `useCopyToClipboard` [cite: frontend/src/components/Items/columns.tsx:11-39].
2. `AddItem` validates `title` (required) and `description` (optional) [cite: frontend/src/components/Items/AddItem.tsx:33-36] and calls `ItemsService.createItem`, invalidating `["items"]` [cite: frontend/src/components/Items/AddItem.tsx:55-66].
3. `ItemActionsMenu` renders `EditItem`/`DeleteItem`, which call `ItemsService.updateItem` (via the same form shape as `AddItem`) / `ItemsService.deleteItem` [cite: frontend/src/components/Items/ItemActionsMenu.tsx:18-33, frontend/src/components/Items/DeleteItem.tsx:33-47].
Ends by writing to the backend's Items API.

**Signed-in user manages their own account**
1. `UserInformation` seeds the form from `useAuth`'s `currentUser` and toggles an edit mode [cite: frontend/src/components/UserSettings/UserInformation.tsx:31-49].
2. On submit it diffs only the changed fields before calling `UsersService.updateUserMe`, then invalidates all queries so `currentUser` refetches [cite: frontend/src/components/UserSettings/UserInformation.tsx:51-76].
3. `ChangePassword` validates current/new/confirm password with zod and calls `UsersService.updatePasswordMe` [cite: frontend/src/components/UserSettings/ChangePassword.tsx:20-37,54-62].
4. `DeleteAccount` renders `DeleteConfirmation`, which calls `UsersService.deleteUserMe` then logs the user out via `useAuth`'s `logout` [cite: frontend/src/components/UserSettings/DeleteAccount.tsx:3-13, frontend/src/components/UserSettings/DeleteConfirmation.tsx:27-33].
Ends by writing to the backend's "me" endpoints, with a forced logout as a side effect of self-delete.

**App chrome: sidebar navigation and theme**
1. `AppSidebar()` composes `Logo`, `SidebarAppearance`, `Main`, and `User` inside the `ui/sidebar.tsx` primitives [cite: frontend/src/components/Sidebar/AppSidebar.tsx:27-39].
2. `Main()` highlights the active nav item by comparing `useRouterState`'s pathname to each item's `path` and renders a `RouterLink` [cite: frontend/src/components/Sidebar/Main.tsx:23-52].
3. `SidebarAppearance`/`Appearance` read and set the theme through `useTheme()`, backed by `theme-provider.tsx`'s context, which persists the choice to `localStorage` and toggles the `dark`/`light` class on `document.documentElement` [cite: frontend/src/components/Common/Appearance.tsx:25-27,69-70, frontend/src/components/theme-provider.tsx:37-70,92-98].
4. `User()` reads the signed-in user, links to `/settings`, and logs out via `useAuth`'s `logout` [cite: frontend/src/components/Sidebar/User.tsx:43-56].
Ends with no backend write; the only persistence is the theme key in the browser's `localStorage`.

## Where it's fragile
- `AddUser.tsx` and `EditUser.tsx` are the area's hotspots (6 and 5 commits over 239 lines each) [cite: frontend/src/components/Admin/AddUser.tsx:1-239, frontend/src/components/Admin/EditUser.tsx:1-239]. They carry near-duplicate zod schemas and markup for create vs update, with subtly different password rules (required vs optional-and-must-match-if-present) [cite: frontend/src/components/Admin/AddUser.tsx:34-51, frontend/src/components/Admin/EditUser.tsx:34-50]. A password-policy change has to be made in both and kept in sync with the backend's `UserCreate`/`UserUpdate` [cite: backend/app/models.py:30-61]; run `admin.spec.ts`'s password tests after touching either file [cite: frontend/tests/admin.spec.ts:153-179].
- Frontend validation is weaker than the backend's strip-and-reject rule in two places: `AddItem.tsx`/`EditItem.tsx`'s `title: z.string().min(1)` doesn't trim, so a whitespace-only title passes client validation but is rejected by the backend's `strip_title` [cite: frontend/src/components/Items/AddItem.tsx:33-36, frontend/src/components/Items/EditItem.tsx:33-36, backend/app/models.py:103-108], surfacing only as a generic `handleError` toast instead of a field message. The same gap exists for `full_name` on `AddUser.tsx`/`EditUser.tsx` versus the backend's `_strip_full_name` [cite: frontend/src/components/Admin/AddUser.tsx:36-37, backend/app/models.py:20-26]. Changing these forms should follow the stripping convention in `docs/agents/VALIDATION_CONVENTIONS.md` even on the client side, and add/extend a Playwright case for whitespace-only input.
- `Sidebar/User.tsx` types its prop as `user: any` rather than `UserPublic` [cite: frontend/src/components/Sidebar/User.tsx:43], so a shape change from `AppSidebar.tsx`'s `currentUser` [cite: frontend/src/components/Sidebar/AppSidebar.tsx:21,37] would not be caught by the TypeScript check (`tsc`/build step); tightening the type and checking all call sites is safer than leaving it `any`.
- `DataTable.tsx` is shared by both `Admin/columns.tsx` and `Items/columns.tsx` [cite: frontend/src/components/Admin/columns.tsx:13, frontend/src/components/Items/columns.tsx:35] and wraps a newer, opt-in `@tanstack/react-table` API (`tableFeatures`/`rowPaginationFeature`/`createPaginatedRowModel`) [cite: frontend/src/components/Common/DataTable.tsx:1-9,34-54]. A library bump or a pagination change ripples to both tables; the pagination math (page count, "showing X to Y of Z") [cite: frontend/src/components/Common/DataTable.tsx:101-197] has no isolated unit test, only the end-to-end `admin.spec.ts`/`items.spec.ts` which don't exercise paging explicitly.
- `UserActionsMenu.tsx` hides edit/delete for the signed-in user to prevent self-lockout [cite: frontend/src/components/Admin/UserActionsMenu.tsx:23-25]; removing that check would let a superuser demote or delete themselves from the table, and `admin.spec.ts` has no test asserting the menu is absent for one's own row, so a regression there would not be caught by the gate's Playwright run.
