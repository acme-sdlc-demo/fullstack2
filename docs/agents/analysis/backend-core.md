# backend/core

## What it does

This area is the backend's shared foundation: it loads configuration once, opens the one database connection the app uses, and does the two security-sensitive jobs (password hashing/verification and JWT issuing/decoding) that every other backend area relies on rather than re-implementing. It defines no domain concept (no "clinic", "owner" or "appointment" — this is the generic FastAPI full-stack template's Users/Items app, not a veterinary system; the profile's "veterinary clinic" line is stale for this repo) [cite: source:transcript-run-1416470e@r1#T3].

- `Settings` (type, `backend/app/core/config.py:15`) reads environment variables (via `../.env`) into typed fields — API prefix, secret key, token lifetime, SMTP, Sentry, the Postgres URL, first-superuser credentials — and is instantiated once as the module-level `settings` (term, `backend/app/core/config.py:91`).
- `backend/app/core/db.py` creates the single SQLAlchemy `engine` (term, `backend/app/core/db.py:7`) from `settings.DATABASE_URL` and defines `init_db()` (method, `backend/app/core/db.py:15`), which seeds the first superuser.
- `backend/app/core/security.py` defines `create_access_token()` (method, `backend/app/core/security.py:22`), `verify_password()` (method, `backend/app/core/security.py:29`) and `get_password_hash()` (method, `backend/app/core/security.py:35`), all built on a `PasswordHash` configured with Argon2 then bcrypt hashers [cite: backend/app/core/security.py:11-16].

## Main flows

1. **App start-up / configuration load.** Importing `app.core.config` runs `Settings()` (type, `backend/app/core/config.py:15`), which reads `../.env` [cite: backend/app/core/config.py:18], applies the `_use_psycopg_driver` validator to rewrite a `postgres://`/`postgresql://` `DATABASE_URL` to `postgresql+psycopg://` [cite: backend/app/core/config.py:33-40], defaults `EMAILS_FROM_NAME` to `PROJECT_NAME` [cite: backend/app/core/config.py:51-55], and runs `_enforce_non_default_secrets` which warns (if `FASTAPI_ENV == "development"`) or raises `ValueError` if `SECRET_KEY`, the `DATABASE_URL` password, or `FIRST_SUPERUSER_PASSWORD` is still `"changethis"` [cite: backend/app/core/config.py:68-88]. The single `settings` object (term, `backend/app/core/config.py:91`) is then read by `backend/app/main.py:18-35` to set the Sentry DSN, app title, OpenAPI URL path, CORS origin and router prefix — writes/reads: process environment in, a configured `FastAPI` app out.
2. **Login.** `login_access_token()` (`backend/app/api/routes/login.py:24`) calls `crud.authenticate()` (`backend/app/crud.py:45`), which loads the user via `get_user_by_email()` (`backend/app/crud.py:34-37`, a DB read) then calls `verify_password()` (`backend/app/core/security.py:29`) — against a constant `DUMMY_HASH` when no user is found, to avoid a timing side-channel [cite: backend/app/crud.py:48-51] — and, on a bcrypt-only hash, rewrites the user's `hashed_password` with the Argon2-rehashed value and commits [cite: backend/app/crud.py:55-59] (a DB write). On success, `login.py:39` calls `security.create_access_token()` (`backend/app/core/security.py:22`), which signs `{"sub": str(user.id), "exp": ...}` with `settings.SECRET_KEY` and `ALGORITHM = "HS256"` [cite: backend/app/core/security.py:19,25], returning a `Token`.
3. **Authenticated request.** `get_current_user()` (`backend/app/api/deps.py:30`) takes the bearer token (`TokenDep`, `backend/app/api/deps.py:27`) and calls `jwt.decode()` with `settings.SECRET_KEY` and `security.ALGORITHM` [cite: backend/app/api/deps.py:32-33], builds a `TokenPayload`, then reads the `User` row by id from a `Session` opened on the core `engine` via `get_db()` (`backend/app/api/deps.py:21-23`) — a DB read keyed by the id in the token's `sub` claim.
4. **First-run seeding.** `app.initial_data.init()` (`backend/app/initial_data.py:12-13`) and the test fixture `db()` (`backend/tests/conftest.py:16-18`) both open a `Session(engine)` and call `init_db()` (`backend/app/core/db.py:15`), which looks up `settings.FIRST_SUPERUSER` by email [cite: backend/app/core/db.py:24-26] and, if absent, builds a `UserCreate` from `settings.FIRST_SUPERUSER`/`FIRST_SUPERUSER_PASSWORD` and calls `crud.create_user()` [cite: backend/app/core/db.py:28-33], which calls `get_password_hash()` (`backend/app/core/security.py:35`) before the DB write — writes one `User` row the first time it runs.

## Where it's fragile

- `config.py` is the area's hotspot (score 637: 7 commits x 91 lines) [cite: backend/app/core/config.py:1-91], and `settings` is read in 16 other files per the graph's "most depended on" list — any field rename or default change (e.g. `API_V1_STR`, `FRONTEND_HOST`, `ACCESS_TOKEN_EXPIRE_MINUTES`) ripples into routes, deps, alembic and tests that read it by name (e.g. `backend/app/api/deps.py:12,17`, `backend/app/alembic/env.py:23,34`). Change a field name and grep every `settings.<FIELD>` use before editing, and check `backend/tests/utils/utils.py:6` and `backend/tests/conftest.py:7` too.
- `_enforce_non_default_secrets` (`backend/app/core/config.py:79-88`) and `_check_default_secret` (`backend/app/core/config.py:68-77`) gate startup behind `FASTAPI_ENV`: in anything other than `"development"` a leftover `"changethis"` secret raises instead of warning [cite: backend/app/core/config.py:74-77]. There is no dedicated test file for `app/core` (the graph lists `0 test` files read for this area's sibling test folders under `backend/tests` that target it directly), so a change here should be checked by running the existing suite with `FASTAPI_ENV=development` as the gate does, since that is what currently keeps this check from raising in CI/tests.
- `security.py`'s `ALGORITHM = "HS256"` (`backend/app/core/security.py:19`) and the two-hasher `password_hash` (Argon2 primary, bcrypt fallback, `backend/app/core/security.py:11-16`) are read from two places independently — `create_access_token()` encodes with it (`backend/app/core/security.py:25`) and `get_current_user()` decodes with it from `backend/app/api/deps.py:33` — so the algorithm name and `SECRET_KEY` must stay in sync between signing and verification; changing one without the other breaks every authenticated request silently (tokens fail verification, not a crash at startup).
- `engine` (`backend/app/core/db.py:7`) is a single module-level `create_engine(...)` shared by the app and by `backend/tests/conftest.py:8` — tests and the app depend on the exact same engine wiring (`pool_pre_ping=True`, the DSN rewrite in `_use_psycopg_driver`); a change to the DSN scheme handling in `config.py:33-40` affects migrations (`backend/app/alembic/env.py:34`) too.
